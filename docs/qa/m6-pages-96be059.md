
**这里要更正一个判断**：审核验用「三通道比值 10/16=0.625、9/18=0.500、7/21=0.333 不一致」否掉压暗——那是**拿原版底色当基准**算的。拿**我方抽屉真实底色**当基准，三个比是：

```

比值    10/26 = 0.385   9/22 = 0.409   7/18 = 0.389      ← 近似均匀 0.39
```
`FLAG_DIM_BEHIND` 默认 `dimAmount = 0.6` → 透过率 0.4，与 0.39 吻合。**所以压暗确实存在**，只是被压暗的对象是我们的抽屉，而不是原版那块已经偏亮的底色。

**待一次设备确认（3 秒可做）**：开抽屉、**不弹联系人卡片**，截一张取同区底色。
- 若测到 `#1A1612` → 压暗存在（弹层 dim），原版无此压暗 → 差异归「弹层压暗」；
- 若测到 `#0A0907` → 抽屉底色本身就比代码值暗（或另有遮罩）→ 差异归「抽屉底色」。

两种情况结论不同，所以这条**未确认**，不改判据、不写成缺陷。

### 2.5 抽屉底色：不用设备就已定性（2026-11-09 21:0x 补）

**这一步靠亮度天花板算出来的，不靠再拍一张。** 原版 `contact.png` 弹层之外的抽屉区里，文字与金色图标的实测亮度：

```
原版 金色图标 (168,143,98)   亮字 (165,157,139)   灰字 (156,156,156)
若原版也按 0.4 压暗 → 反推原始值必须 = 实测 ÷ 0.4
   (168,143,98)/0.4  = (420,358,245)     R 超 255
   (165,157,139)/0.4 = (412,392,348)     R/G/B 全超 255
   (156,156,156)/0.4 = (390,390,390)     全超 255
```
**算术上不可能** ⇒ **原版 contact 弹层没有 0.4 这种压暗**；它的 `#101215` 就是抽屉面板本色。

**所以总监那条反推（`#101215 ÷ 0.4 ≈ #282D35`）不成立**——它假设两边压暗一致，而亮度上限把该假设否掉了。
我方那侧压暗是真的：`#1A1612 × 0.4 = (10.4, 8.8, 7.2)`，实测 `(10,9,7)` 逐通道吻合。

**冷暖方向也不一样**（这个与压暗无关，纯底色选择）：
```
原版 #101215 = (16,18,21)   B>G>R  冷灰蓝
我方 #1A1612 = (26,22,18)   R>G>B  暖褐
```
**结论（两条独立缺陷，实现侧）**：
1. `MainActivity:2616` 抽屉面板底色 `Color.rgb(26,22,18)` 与原版 `(16,18,21)` 不符，且冷暖相反；
2. 我方 `contact` 弹层带 0.6 压暗（透过 0.4），原版无此压暗 → 弹层窗口标志（`FLAG_DIM_BEHIND`/`dimAmount`）需对齐原版。

判据侧：`contact` 的 `THEME` 期望 `#101215` 量的是**弹层背后的抽屉**，不是联系页；应改为「弹层内底色」（两边都是纯白）。这一点与 §2.4 一并有效。

证据：`docs/fidelity/m3/contact.png`（原版）、`docs/fidelity/m3/stage3/a-account.png`（我方抽屉、无弹层，底色 `(26,22,18)` 与代码值一致）、`act-contact.png`（我方弹层态）。
