## 3. 判定口径（三档结论）

对每条报告条目，核验后只给以下三档之一，禁止「基本属实」这类含糊结论：

| 结论 | 成立要件 |
|---|---|
| **确认** | 文件存在；行号范围在文件内且**行号所指内容与报告片段逐字一致**（含中文标点、`\u200c` 等不可见字符）；上下文完整，未被别处代码处理；定级与章程/矩阵口径不冲突 |
| **修正** | 缺陷现象成立，但至少一项需要改：行号偏移、片段不完整/拼接、上下文缺失导致描述过头、定级偏高/偏低、影响面判断错误、触发条件写错。**必须给出修正后的完整三件套与定级** |
| **驳回** | 命中 §3.1 任一硬理由。**必须指出具体证据**，不接受「依据不足」作为唯一理由 |

### 3.1 驳回硬理由（五类，逐条举证）

1. **行号不存在**：行号超出文件总行数，或该行号为空白/注释，与所述代码无关。
2. **片段与源码不符**：引用文字与基线原文不能逐字对上（错字、增删、把两处拼成一段、把别的分支代码当基线）。
3. **上下文缺失导致误判**：报告引用点前后有分支/开关/提前 return/重载把它处理掉了。
4. **已被别处代码处理**：同一缺陷在别的文件已被处理（如 `MainActivity` 里 `p01Enabled` 分支、`applyTrustState()`、`captureMap()` 的 PixelCopy 退路）。
5. **已定设计意图 / 已登记状态**：命中 §6 豁免表（D-001..D-009、矩阵「有意省略/有意解除/等价替代」），或台账已闭环（`bugs.md` BUG-001..005 已修复且本轮基线可验）。

### 3.2 证据等级复核

- **已证实**：有代码路径或可复现推演。核验时要能指出「从哪一行进、经过哪几行、到哪一行出」。
- **高度可疑**：有代码依据，触发条件未完全确认。报告必须写清**缺哪一条触发证据**。
- **待确认**：线索不足。不得写进正式缺陷清单；核验时检查报告是否把它混入「正式清单」。

## 4. 逐条核验固定流程（S1–S6）

对每条条目按序执行，任一步失败即按 §3 定档：

- **S1 落点**：`grep`/`read` 回到基线文件，确认路径拼写与矩阵 §3 一致（大小写、`\` 分隔、有无 `app/` 前缀）。
- **S2 行号**：读报告所给行号范围；若行号偏移，记录**真实行号**与偏移量（如 −0 / +3）。
- **S3 逐字**：报告片段与源码逐字比对；中文引号、`__`、空格、`\u200c` 都要看。拼接多段引用的，逐段分别核对并在结论里注明「拼接但各自属实」或「拼接失真」。
- **S4 上下文**：向前后各读 ≥20 行，确认触发条件（哪个入口、什么状态、是否被开关/分支短路）。
- **S5 交叉处理**：在同一模块内 `grep` 相关标识符，确认是否已被别处处理（如 `p01Enabled`、`trustEnabled`、`isDebuggable()`、`injectedHeading != null`）。
